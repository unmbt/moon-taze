# 需求规格

版本：0.2。状态：待实现。本文的“必须”是验收条件；“不支持”是本版本边界，不允许静默模拟为已支持。目标行为未缩减，交付优先级与阶段门槛见 [推进路径](tasks.md#roadmap)。

## 1. 用户场景与成功标准

| 场景 | 用户期望 | 成功标准 |
| --- | --- | --- |
| 日常维护 | 知道当前声明的依赖有哪些兼容更新 | 默认调用不修改项目，清楚展示旧版本、目标版本及跳过原因 |
| 主动升级 | 选择 patch、minor、major 等策略 | 相同元数据与配置产生相同计划，未经允许不降级 |
| 仓库维护 | 一次检查多个 MoonBit 模块 | 正确识别工作区、本地依赖和扫描边界，同一模块查询去重 |
| 人工选择 | 只更新部分依赖或选择其他候选版本 | 交互取消不写文件，确认结果与写入结果一致 |
| CI 检查 | 消费机器输出并判断是否需要维护 | stdout 是有效 JSON，退出码区分发现更新与执行失败 |
| 自动化集成 | 在其他 MoonBit 工具中复用检查能力 | 只读检查和写回分离，能注入 Registry、文件系统和时钟 |

“当前版本”始终指 `moon.mod` 中的声明版本。moon-taze 不实现传递依赖求解，不保证推荐版本兼容源代码；更新后的编译验证是独立的显式操作。

## 2. 功能需求

| ID | 要求 |
| --- | --- |
| REQ-001 | 解析 `moon.mod` 的普通依赖 import，支持注释、多段 import 和任意排版；保留原始源码位置。重复模块声明、非法版本及不明确的依赖语法必须报告错误。 |
| REQ-002 | 支持当前模块、`--cwd` 和显式递归发现；默认不递归。忽略生成目录、版本控制目录和其他仓库边界，路径行为跨平台一致。 |
| REQ-003 | 读取 `moon.work` 的成员信息，识别成员之间的本地依赖。仅因递归扫描看见同名模块不能将注册表依赖当成本地依赖。 |
| REQ-004 | 从 Mooncakes 获取模块版本列表、latest 指针和撤回状态，按需获取指定版本发布时间；响应必须校验，错误不能伪装成“已是最新”。 |
| REQ-005 | 使用 SemVer 2.0.0 比较，包括数字预发布标识和 build metadata；禁止降级及只有 build metadata 不同的无效更新。模块标识不随更新改变。 |
| REQ-006 | 提供 `default / major / minor / patch / latest / newest / stable / next` 八种模式，裸版本默认参与。精确定义见 [D-05](design.md#d-05)。 |
| REQ-007 | 支持依赖名称匹配、包含/排除、候选版本排除和逐依赖策略；排除优先于包含。规则必须可解释，未知规则语法报错。 |
| REQ-008 | 支持 `moon-taze.json`，配置优先级为 CLI > 配置 > 默认值；逐依赖策略覆盖合并后的全局模式。配置不允许隐式开启写入或外部进程。 |
| REQ-009 | 默认输出检查预览，支持显示全部依赖、按变更/名称/时间排序和按项目分组；区分可更新、无更新、跳过和错误。 |
| REQ-010 | `--write` 应用已验证的更新计划；只替换版本文本，写前检测文件变动，单文件完整替换，明确报告多文件部分成功。 |
| REQ-011 | `--interactive` 提供依赖选择、候选版本切换和最终确认；取消不写入，非 TTY 明确报错，退出后恢复终端状态。 |
| REQ-012 | `--json` 输出有版本号的稳定结构，包括模块、变化、跳过、诊断和应用结果；stdout 不夹杂进度条、ANSI 或日志。 |
| REQ-013 | 退出码 0 表示成功，开启 `--fail-on-outdated` 后发现候选更新返回 1，执行错误返回 2；错误优先。 |
| REQ-014 | 请求使用有界并发、超时和重试；同一运行内相同资源的请求去重，取消后停止排队与重试。 |
| REQ-015 | 提供内存与磁盘缓存，TTL 默认 30 分钟，`--force` 绕过旧缓存；损坏缓存不影响正确查询，不静默使用过期数据。 |
| REQ-016 | 支持成熟期及豁免规则，默认关闭，裸 `--maturity-period` 为 7 天；开启后缺少可靠时间的候选不得被当成成熟版本。 |
| REQ-017 | 支持发布时间差展示和时间排序；缺失时间显示未知。`newest` 不依赖响应数组顺序或用 SemVer 冒充发布时间。 |
| REQ-018 | 提供 MoonBit 库 API，检查与应用分离，核心算法可离线测试；公共类型归属于对外包，提供进度和应用回调。 |
| REQ-019 | 显式 `--verify` 在成功写回后调用 `moon check`，遵循目标项目配置；失败报告但不自动还原已写入内容。 |
| REQ-020 | 保持操作边界：不新增依赖、不迁移清单、不修改模块名、传递依赖、`moon.pkg`、工具链或全局软件；错误和不支持的输入有明确提示。 |

## 3. 非功能要求

| ID | 要求 |
| --- | --- |
| NFR-001 | 确定性：相同输入快照、配置、Registry 元数据及注入时间得到相同候选与排序；并发完成顺序不改变结果。 |
| NFR-002 | 写入完整性：没有更新时字节不变；有更新时只有选定版本区间改变。查询或解析失败时不得自动部分更新。 |
| NFR-003 | 可测试性：常规测试无外网、无真实用户缓存及项目写入；时钟、网络、文件系统、终端、进程可替换。 |
| NFR-004 | 可移植与可诊断：最终支持三平台 Native；诊断包含稳定代码、模块/路径定位、原因和必要的恢复信息；运行时能力以实测为准。 |

## 5. 范围和约束

- 支持的是普通注册表 import。已弃用的二进制依赖 import 识别后报告 `unsupported_dependency_kind`，不纳入写回；不将其与普通 import 混淆。
- 本地依赖仅按实际工作区成员关系判断，不根据目录名、包名碰巧相同或清单版本号推断。
- 旧格式单独存在时返回不支持错误；新旧格式并存时返回歧义错误，不擅自选择、转换或删除文件。
- `moon.mod` 的版本是 MoonBit 最小版本选择的输入，不是 npm 的锁定版本。该工具只提高声明，不保证实际依赖图完全相同。
- 运行检查无需 Node.js、npm 或 Git。只有用户请求更新后验证时才调用 `moon`；Native 产物的系统运行库依赖必须在发行说明中列出。
- 每个适用功能完成后必须满足关联验收，不通过减少候选、隐藏错误或改变默认行为来让测试通过。
